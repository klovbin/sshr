# How sshr protects hosts and secrets

What happens to passwords, keys and synced data, [USAGE.md](USAGE.md) says how to use each feature, [WHY.md](WHY.md) says why it was built this way (Russian)

## Threat model

| Who | What they can do | What sshr does | What is left |
|----|----|----|----|
| someone with the disk (a stolen laptop, a backup) | read `~/.sshr` | passwords and stored keys are sealed with a vault key kept in the system keychain, or in a file under an Argon2id passphrase, a key made with `sshr key new --sk` stays on its token and its handle is useless without it | the host list, addresses and users are in clear, the passphrase file can be guessed offline when the passphrase is weak |
| another user of the machine | open files and sockets | `~/.sshr` and the sockets are 0600 in 0700 folders, the API socket refuses peers of another user | root sees everything |
| someone who learned a password or got a key file | log in as you from sshr | `sshr hwkey require` makes chosen hosts connect from sshr only with a key on a FIDO token, a password or another key is refused before ssh runs | the server still takes what it takes, only `PasswordAuthentication no` and sk keys alone in authorized_keys make the token required for everyone |
| a program running as you | everything you can | extensions get no secret from sshr in their environment, every sshr process closes its memory: not dumpable on Linux (no ptrace, no `/proc/pid/mem`), `PT_DENY_ATTACH` on macOS, no core files, `SSHR_ALLOW_DEBUG=1` turns that off for a debugger and sshr warns about it on every start | it can read the keychain the way sshr does, read the memory of sshr on Windows, edit the audit log, root can still read any memory |
| the sync server | store, drop, hold back and reorder what devices upload | hosts are encrypted and signed per device, manifests are chained and MAC'd, a new device is trusted only after comparing fingerprints | it sees the number of hosts, push times and device names, it can show two devices different histories, compare the state fingerprint |
| a stolen or hostile sync device | push hosts signed by a trusted device | it never gets private keys stored on other devices, 1Password and Bitwarden references, key files and agents do not follow a host that moved, permissions for commands live in settings that never sync | until it is removed it can rename hosts and point new ones anywhere, remove it with `sshr sync remove-device` on the primary device, a device that is not primary cannot add or remove devices or change the vault key, every device refuses such a manifest from it and keeps its hosts, sshr-sync checks the same rule and refuses such a manifest, a token revoke and an approval from a device that is not primary, on S3, WebDAV and Supabase every device holds the store credential, there a refused manifest can still become the head and stop the sync of the account (#292) |
| a hostile ssh server | answer with anything | the host key is checked by ssh, a saved password is tried once and only at a password prompt, its output reaches an assistant marked as data | it gets the password of that host, a login it was meant to get |
| an AI assistant or a script | call `sshr mcp` or `sshr serve` | commands are off by default, can be limited to chosen hosts, asked about one by one, logged, no secret goes in or out | an assistant allowed commands on a host can do there what that login can |
| a web page | send requests to localhost | requests with an `Origin` and a non-loopback `Host` are refused, a TCP port needs a token | none known |
| a tampered release file | replace a download | install.sh checks `sha256sums.txt`, releases carry a build attestation | the checksum list comes from the same release, a signature with a pinned key is #146 |
| an extension you install | run as you | it is pinned by hash and shown before install, it gets no secret from sshr | it can do anything you can, read the code first |

## Saved passwords and keys

- a saved password or a key kept in sshr is sealed in the host file with XChaCha20-Poly1305, the host ID and field name as associated data, so a value copied to another host or field does not open, a password and a stored key also carry their address, user, port, jump hosts and gateway, so an address changed in the file outside sshr does not open them, an edit in sshr seals them again, a host moved on another device takes the synced password with it but not the key stored here, which waits to be pasted again, as a 1Password reference is dropped, passwords and keys saved by an older version are sealed again this way on the next start
- the vault key is 32 random bytes in the system keychain (Secret Service, macOS Keychain, Windows Credential Manager), never on disk, created once under a file lock so two processes cannot make two keys, with the keychain a running sshr zeroes and forgets its cached copy 15 minutes after its last use (`vault_idle_minutes`), the copies inside the ciphers made from it are not zeroed and stay in memory until they are collected, under a passphrase the key is kept for the whole run
- every keychain call has a 5 s limit, a locked keyring that nobody answers does not hang sshr, after a call ran out the keychain is not asked again for a minute, so a sync of many hosts does not wait 5 s for each, with no keychain a saved password cannot be added, ask mode and key files keep working
- a missing keychain (no session bus, no Secret Service, no default collection), a locked one (its unlock was dismissed) and one that did not answer get their own message, all are `ErrNoKeychain` to the app (`ErrKeychainMissing`, `ErrKeychainLocked`, `ErrKeychainTimeout`), macOS and Windows are not told apart yet (#153)
- `sshr list` and the host form never decrypt, an empty password field keeps the saved one
- a reset keychain or `~/.sshr` copied to another machine makes saved secrets unreadable, sshr asks to save them again
- `~/.sshr/vault/key-check` holds a hash of the vault key (not the key), when the keychain lost the key or holds another one (a reset, another keychain program) sshr says so and does not make a second key over the secrets sealed with the first, bringing the item back or deleting that file and saving the secrets again ends it
- a key with a passphrase is opened once when added and stored without it, the vault encryption takes its place
- `sshr vault passphrase` keeps the vault key in `~/.sshr/vault/vault-key.json` instead, wrapped with XChaCha20-Poly1305 under a key from Argon2id (t=3, 64 MiB, 4 lanes, a random 16-byte salt, the parameters in the file and capped when read, so a crafted file cannot exhaust memory), off by default, the passphrase is asked once per run and never read from stdin, `sshr mcp` takes it only from `SSHR_ASKPASS`, a wrong one opens nothing and never makes a new key

## How a password reaches ssh

- ssh runs sshr itself as `SSH_ASKPASS`, the helper takes the password from a unix socket in a 0700 directory that answers one client with the right token and closes, the password is never in a file, an environment variable or a command line
- only a password prompt gets it, the host key question, key passphrases and one-time codes are asked on the terminal
- a saved password is tried once (`NumberOfPasswordPrompts=1`), retries only feed fail2ban

## How a key from sshr or 1Password reaches ssh

- sshr serves the key from an ssh agent inside its own process for as long as ssh runs, on a unix socket in the 0700 control directory (a named pipe on Windows), the private key is only in memory, on Linux and macOS the agent answers only sshr and the processes it started (ssh, the ssh of a jump host, mosh), told by the peer process of the socket and its parents, a program of the same user outside sshr cannot use the key while a session runs, a program sshr itself started can: in a long running `sshr serve` or `sshr mcp` that includes the local commands of hosts and the commands of extensions, on Windows the pipe lets in any process of the user
- ssh gets `-i <id>.pub -o IdentitiesOnly=yes -o IdentityAgent=SSH_AUTH_SOCK -o ForwardAgent=no`, it offers only this key and the server cannot reach the agent
- 1Password items are read with `op read` on every connect, a new item gets the password as a JSON template on stdin, not in arguments
- Bitwarden items are read with `bw get password` and `bw get item` (the key is in the item's `sshKey` field) on every connect, with the session from `BW_SESSION`, sshr never sees the master password

## Sync

- every device has its own keys from a 32-byte seed in the keychain: Ed25519 for signing and ML-KEM-768 + X25519 (X-Wing) for receiving the vault key, there is no master password to guess
- a random vault key encrypts each host (XChaCha20-Poly1305, account, host ID and key epoch as associated data, padded to 512 bytes), each device gets the vault key in its own HPKE envelope
- the manifest lists hosts, blob hashes and trusted devices, it is MAC'd with the vault key, signed by the pushing device and chained to the previous manifest, a device accepts only a chain that continues what it saw, signed by a device it trusts, every manifest of the chain is checked by signature, the MAC with the vault key on the manifest it applies, so a device that missed several key changes still catches up
- a new device is trusted only after comparing its fingerprint on both screens, the fingerprint covers its signing key and the encryption key the vault key is sealed to (a server that swaps either changes it, a joined device also refuses an account that lists it with another encryption key), the invite code carries the inviting device's fingerprint, so the server can neither add its own device nor impersonate the inviter
- saved passwords travel inside the encryption and are sealed again on the receiving machine, private keys kept in sshr never leave their device
- 1Password and Bitwarden references never sync, a host from another device keeps the reference set on this machine only while its address, user, port and jump stay the same, otherwise it falls back to asking, otherwise one stolen device could point every other device at a different 1Password item and collect it
- a key file path, an agent and its chosen key follow the same rule: the ones set on this machine stay (empty ones too) while address, user, port and jump stay the same, a host new to this machine keeps the ones it brings, a host from another device that now points elsewhere falls back to the default ssh keys and says so, so a stolen device cannot make ssh offer another key of yours to a new server
- removing a device revokes its token first, then rotates the vault key and re-encrypts every host, the new key is delivered to the other devices only after the manifest without that device is written, a removal that loses the race to another push plans again from the newer state, a delivery cut short resumes on the next sync of that device and the others wait for it
- limits: a new device trusts whatever the server shows first, a server can show two devices different histories (compare the state fingerprint in `sshr sync status`), the server sees host count, push times, addresses and device names, and can hold back changes, a removed device keeps what it downloaded

- a sync through an object store (an S3 bucket with `sshr sync init --backend s3`, a WebDAV folder with `--backend webdav`, a Supabase project with `--backend supabase`) keeps the same encryption, signatures and chain, the next manifest is created only if its name is free, so two devices never both win, what the store cannot do that sshr-sync does: every device shares one store credential, so a removed device can still write and delete objects and a device waiting for approval can read every object (ciphertext, the device list, the plain manifest bodies with entry IDs and stamps), rotate the store credential after removing a device (`sshr sync remove-device` says so, `sshr sync store-key --key-id <new>` saves the new key on each device that stays), whoever holds it can block the account: a deleted manifest reads as a rollback, a planted one fails verification, every device then stops syncing and no device gets a key or a host from it, the account works again once the bad object is deleted from the store by hand (the error names the change number, the object is manifests/<that number with 20 digits>), objects are capped at the sizes of sshr-sync and names of another shape are ignored, the device that pushes deletes manifests more than 1000 changes old, as sshr-sync keeps them, the store secret sits in the keychain as `sync-store-secret`, never in the sync state, setup refuses a store that writes over an object on a second create, S3 and R2 document that create as atomic, MinIO takes the header but its atomicity under concurrent creates is not verified, no WebDAV server makes the create strictly atomic: Nextcloud and ownCloud check the name before they take the upload lock, so two creates at the very same moment can rarely both succeed, Apache mod_dav checks and then renames a temp file, so concurrent pushes there can overwrite a manifest, a device whose manifest was overwritten stops with "does not follow the last change this device saw" and pairs again, the WebDAV password is sent in Basic auth over HTTPS only and never across a redirect, a Supabase project decides the create with the primary key of a table, so it is atomic, the device holds the publishable key (public by design) and a 256-bit sshr key, the project stores only its sha256, the table is in a schema the Data API does not expose and only SECURITY DEFINER functions that check the key reach it, every call is a POST and the key goes in a header, never in a URL, the sshr key is shared by all devices like a bucket key, `supabase-sql --replace` and `store-key` replace it after a device is removed

## Sync server

- stores device public keys, encrypted blobs and signed manifests, it cannot read hosts, it can only lose data or refuse service
- each device has its own bearer token, the server keeps its SHA-256, new accounts and joins are limited to 10 an hour per address, a joined device does nothing until approved
- a manifest is replaced only with `If-Match` on the current counter and only when every blob it names is stored, two devices pushing at once cannot overwrite each other
- blobs are content addressed (SHA-256, 1 MiB at most, 20000 and 256 MiB per account), unused blobs go after a day, the last 1000 manifests are kept for the history check
- TLS 1.3 only, plain HTTP only on loopback, one server per data directory

## MCP and REST

- neither returns or accepts passwords, private keys or 1Password and Bitwarden references, a host linked to a password manager is added in the app or the CLI
- `sshr mcp` listens on nothing, the assistant runs it as a child process over stdin and stdout, every command is logged to stderr quoted, so control characters in it cannot forge lines, `sshr serve` logs its commands the same way
- `sshr serve` listens on a 0600 unix socket by default and refuses a client that runs as another user (the socket names its uid on Linux and macOS, Windows has the ACL of the socket only), a TCP port only on loopback and only with the token from `~/.sshr/api-token`, requests with an `Origin` header (web pages) or a non-loopback `Host` (DNS rebinding) are refused
- what `sshr mcp` hands the model from outside is marked as data: remote output sits between markers with a nonce of the call, ssh errors, banners and the text of hosts (names, tags, sessions written on another device) lose escape sequences, control, bidi, zero-width and tag characters, so a server or a stolen device cannot hide instructions in them, the REST API returns raw bytes to programs
- with `--audit` (off by default) both append every upload, command, host change and tunnel to `~/.sshr/audit.jsonl` (0600), the client, the host, the exit code, never a secret, a command is kept as length, first word and an HMAC with a key in `~/.sshr/audit.key` so a password typed into it cannot be guessed from the log, a start that cannot be written stops the action, five old files stay after rotation, the log is not tamper-evident, any process of the same user can edit or remove it, the client name of `sshr mcp` is what the client says it is
- `"confirm_commands": true` makes `sshr mcp` ask the user before each command through MCP elicitation and run only after an explicit yes, every other answer, no answer in 5 minutes, a gone client or a client without elicitation refuses, the REST API refuses commands, the question is only as good as the client's dialog, a client that answers it on its own defeats it
- a recovery kit (#150) is a device of the account whose seed is on paper, the rules let it only claim the account and, after the wait the primary chose (at least a day, 7 by default), hand it to one new device, sshr-sync keeps the time of the claim and refuses an early hand-over, every device of the owner notes when it saw the claim, warns and refuses a hand-over before the wait by its own clock or one whose claim it never saw, the primary device cancels by removing the kit device, which changes the vault key, a fresh machine checks an anchor entry only the seed opens, so a hostile server cannot show it a made-up account, and refuses a head older than the counter printed on the kit, limits: the paper holder reads the hosts at once, the wait guards the account and not what was synced, a device that was ever in the account knows the anchor value, together with a hostile server it could show a fresh machine a made-up account, a thief with the paper (and its passphrase, if set) while the owner opens no device for longer than the wait gets the account on the server, the owner keeps the hosts and starts a new account, on S3, WebDAV and Supabase the store checks no wait, a key rotation committed but not delivered when the last device died cannot be recovered
- the local commands of `sshr hooks` run on this machine as the user, so they are off until `sshr hooks on` and live in settings.json, which never syncs, no import, sync, `sshr serve`, `sshr mcp` or extension writes them, the host reaches them only as environment variables (`SSHR_HOST` and the like), a command that passes them to `eval` would let a host changed on another device inject shell code, quote them
- `sshr commands only` limits commands to the hosts of `sshr commands allow`, the list is in settings.json (never synced) and each entry is bound to the address, user, port, jump and gateway of the host and of the saved hosts it jumps through, a stolen device that repoints a host does not inherit its permission, an sshr older than these settings ignores `commands_listed_only`, `command_hosts` and `confirm_commands` and runs commands on every host without asking, so an assistant must not be set up with an older binary
- running commands is off by default in both, each runs at most 8 uploads, commands and tunnel starts at once, an upload holds its body in memory

## Extensions

- sshr runs nothing you did not install: an extension runs only from `~/.sshr/extensions/<name>/`, only when no command of sshr has its name, never from PATH, and a built-in command always wins
- `sshr ext install` shows the manifest, the command, the commit and a hash of the files and asks, a git address is fetched with a shallow clone over https or ssh only, nothing of the clone is run, links and special files are refused, git runs without your global and system git config and with an empty HOME, so a smudge filter set there never runs on a repository of a stranger, also on git older than 2.32, a private repository is installed over ssh, a proxy comes from HTTPS_PROXY and not from gitconfig
- every file of the folder is hashed at install (paths, executable bit, content, a `.git` folder too) and checked before every run, a `git pull` in the folder, a hand edit or an added file stops the run until you install it again, the pin is kept in `~/.sshr/extensions/.pins.json`, not in the folder, so a folder that arrives by other means, as a dotfiles checkout or a restored backup, is not trusted until `sshr ext install` pins it
- an extension never receives a secret from sshr: `SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE`, `BW_SESSION` and the other `BW_` credentials, `OP_SESSION_*`, the 1Password service account and connect tokens and every `SSHR_` variable of a running sshr are removed from its environment, it is given no password, key or secret reference, only a fixed list of host fields reaches it
- limits: an extension runs as you and can do anything you can, including reading `~/.ssh` and `SSH_AUTH_SOCK`, running `sshr connect`, `sshr export` or `sshr sync` through `SSHR_BIN` and reading `~/.sshr`, so "no secret from sshr" means none in what sshr hands it, not that it cannot reach them as you, the hash protects against a changed file and not against a bad extension, read the code before you install it, the check and the run are two steps, so someone who can already write to your `~/.sshr` could swap a file between them
- an importer hands over hosts in a fixed shape (name, address, port, user, key file path, jump, session, tags, forwards), every other field, a password or a key among them, is dropped with a warning, the host gets an ID made from the extension and its own key, so an importer cannot overwrite a host of another source or one you added, and the checks of the store (address, user, forwards) run before anything is saved
- nothing about extensions syncs and neither MCP nor the REST API lists or runs one
- the community catalog (`sshr ext search`, `sshr ext install <name>`) is off until `sshr ext community on`, which says that nobody reviews the code of catalog extensions, it is read over HTTPS only when one of those runs, an entry pins a full commit and an install checks that this commit is what got checked out, a newer push to the repository is not installed, entries are checked for their shape and not for their code, a name listed twice is not installed at all, description and author have control characters removed before they reach the terminal, a catalog entry is not a review, the install says so before the yes

## Export to ssh config

- passwords and keys kept in sshr or 1Password are not exported
- a value ssh could read as another option (a newline, a quote, a space in an address) skips the host, so a synced host cannot add `ProxyCommand` to your config
